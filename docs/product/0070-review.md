# 0070 — 评审

对 [0001](0001-proposal.md)–[0005](0005-pseudocode.md) 的评审。按"能不能站住"排序，不按文章顺序。每条给出证据、代价、以及一个可以立刻动手的替代方案。

**一句话结论：方向和场景是对的，但三个核心主张里有三个都站不住，而真正决定成败的那部分被一行代码带过。建议把 12 周计划改成 2 周的一个垂直切片，先证明能不能跑通，再谈商业化。**

---

## 1. 三个差异化主张，逐条核对

### 1.1 PTC 不是"内核解析脚本再逐个调用工具"

PTC（Programmatic Tool Calling）的定义是：模型写一段代码，在一个代码执行容器里跑，工具从代码内部被调用，**中间结果留在容器里，只有最终结果回到上下文**。节省的不只是轮次，主要是上下文。

0005 的 `PTCEngine` 做的是另一件事：

```ts
const actions = this.parseScript(script);
for (const action of actions) { await tools.invoke(...); await this.confirmUserApproval(action); }
```

这是"批量队列"，不是 PTC。三个问题：

1. **模型在看不到中间结果的情况下预测所有步骤。** 第 3 步的文件内容取决于第 2 步 `read` 的结果。串行 Agent 能自适应，批量脚本不能。一旦某步失败，整段脚本要重新生成，比串行更贵。
2. **每家 API 本来就支持一个 assistant 轮次里返回多个 tool_use 块**，也就是并行工具调用。仓库现在用的 `pi-ai` 已经支持。所以"轮次减少 45%"要先说清楚基线是什么。如果基线是"一次一个工具调用"，那不是今天的竞品，是 2023 年的竞品。
3. **`confirmUserApproval` 在循环里，把收益全部吃掉。** 40 个文件的批量重构 = 40 次弹窗。PRD §5 又要求"所有命令执行都弹出人工审批弹窗"，两条需求互相取消。

**替代方案**：把"PTC"重新定义为一件真事，也就是**一次批准一个计划，执行时由策略引擎逐条判定**。用户看 DAG 和文件清单，批一次。之后读操作自动放行，写操作只检查路径是否在白名单内，违例即停。这样批量才有意义，审计也更干净。真正的 PTC（容器内循环）可以做，但那是接一个代码执行沙箱，不是自己解析脚本。

### 1.2 DAG 调度器已经在依赖里了，不需要"内核级创新"

`pi-durable` 的 task graph 就是这张图。`dist/harness/task-graph.d.ts`：

```ts
export type TaskGraphState =
  | { status: "pending" | "running"; phase: string }
  | { status: "waiting"; phase: string; on: readonly TaskId[]; policy: JoinPolicy }
  | { status: "completing"; outcome: ... };
```

`waiting + on: TaskId[] + JoinPolicy("failFast" | "allSettled")` 就是依赖等待与汇合。任务有 `owner`、`background`、`abortRequested`，状态来自 Session 的持久化提交，所以进程死掉能恢复。`docs/architecture.md` 的栈图里也写了："pi-durable — sessions, storage, the inbox, **task graph**, compaction, usage, resume. 13,979 lines"。

也就是说：**ADR-0001 与 ADR-0017 已经把这块买了单。** 0005 的 `MasterOrchestrator` 重写了 `Promise.all` 加一个 `filter`，同时丢掉了持久化、abort、join 策略和恢复。"内核级壁垒"不能建立在一个已经开源、已经是自己依赖的库上。

### 1.3 竞品矩阵描述的是 2023 年的竞品

| 文档里的说法 | 今天的事实 |
|---|---|
| Pi：无原生多角色、无任务调度、只能单步调用 | Pi 有 subagent，能并行、能跑脚本化 workflow。这个评审会话本身就带着这样的工具 |
| CrewAI：无任务 DAG | CrewAI 有 `Task.context` 依赖、`async_execution`，还有 Flows 做事件驱动编排 |
| Copilot：只做代码补全 | Copilot 有 agent mode，有开 PR 的 coding agent |

拿这三行去写 README，第一个在 Hacker News 上读过 Pi 文档的人就会拆掉它。而 README 的公信力是一次性的。

**替代方案**：不要在"有没有多 Agent"上竞争。改成在**没有人提供的东西**上竞争，仓库已经有两样：

1. **可判决的验收**：`packages/eval` 有确定性谓词、transcript、离线重放。"5 个 Agent 交付的项目通过了可运行的测试"这句话，竞品都没法说，因为它们的验收是模型自己的评价。
2. **证据链**：`docs/product/README.md` 引的那条规则——页面上每个数字都要有命令能重新生成它。这既是对外的可信度，也是对内的防自欺。

## 2. 真正难的地方，被一行代码带过

0003 §3 第 4 步："Master 调度器汇总全部代码，自动合并文件，检查代码冲突。"

这是整个项目 80% 的难度，而可行性报告 §（二）写的是"不存在技术卡点"。并行写同一个仓库的真实失败：

- 两个 Worker 同时改 `package.json`、`tsconfig.json`、lockfile、`docker-compose.yml`。这些文件**在架构上就必然共享**，按模块切不开。
- 每个 Worker 的 `read → edit` 循环看不到对方的写入。A 读到 `v1`，B 写 `v2`，A 提交基于 `v1` 的编辑。这不是"冲突检测"能修的，因为最后一个写的人赢。
- 两边的脚手架会互相覆盖。前端 Agent 与后端 Agent 都可能创建 `src/index.ts`。
- 语义冲突比文本冲突多：接口字段名不一致，两边都能编译，跑起来 400。

`Promise.all` 在这里是数据损坏的写法，不是并行。

**替代方案（我认为这是本项目唯一真正的技术壁垒）**：

架构 Agent 的产出不是"项目结构建议"，而是一份**可执行的契约**：

```ts
type Plan = {
  files: { path: string; owner: WorkerId }[];   // 所有权清单，路径前缀级
  contract: { endpoints: Endpoint[]; types: TypeDecl[] };  // 跨边界接口
  tasks: { id: string; worker: WorkerId; dependsOn: string[] }[];
};
```

调度器据此做两件事：

1. **每个任务只允许写自己名下的路径。** 越界即失败，而不是"合并时再看"。共享文件（`package.json` 之类）由架构 Agent 独占，Worker 只能提交"请追加这个依赖"的请求，由单写者应用。
2. **每个 Worker 跑在自己的 worktree 里**，完成即提交，Master 做 git 合并。合并失败是显式失败，不是静默覆盖。

这个设计有一个额外好处：**它可以被测量**。空仓库到一个能跑起来的 Web 项目，这就是 `packages/eval` 的 `check` 谓词，可以进 CI。

## 3. 从零重写 Bun 内核：代价算错了

立项书 §1 的"核心壁垒"第二条是性能，PRD §4 是"启动 ≤ 200ms"。`docs/decisions.md` 的 ADR-0003 已经量过这件事：

| Invocation | Wall time |
|---|---|
| `pi --version` (Node) | 415 ms |
| `node dist/bundle/cli.js --version` (Node) | 320 ms |
| `codex --version` via npm shim | 465 ms |
| raw Rust `codex --version` | 10 ms |

那条 ADR 的结论是：**npm 分发路径会抹掉内核的速度优势**，所以不要为启动时间换语言。Bun 单二进制可能做到 50 ms，但换来的东西是：

- 丢掉 `pi-durable` 的 13,979 行：会话、存储、收件箱、任务图、压缩、用量、恢复。全部要重写，且这部分和差异化**毫无关系**。
- 丢掉 `packages/eval` 这个唯一的判决系统。多 Agent 场景下它只会更重要，不会更不重要。
- 交叉编译是逐平台的（`--target=bun-windows-x64` 等），带原生依赖时要在每个平台上预构建。TUI 若需要 PTY，Windows 上会更难。
- 12 周里，4 周做 MVP 意味着"Harness 一周、调度器一周、两个 Agent 一周、PTC 加打包一周"，零缓冲。单人项目零缓冲的排期通常延期一倍。

单二进制本身是对的（装 Bun 的门槛是真的），但它是一个**分发决策**，不是**内核决策**。可以先用 `bun build --compile` 打包现有代码，验证安装体验，之后再决定要不要迁移。

## 4. "内核闭源 + 上层 MIT 开源"无法执行

三处冲突：

1. **已经发出去的 MIT 收不回来。** `k9999@0.6.0` 在 npm 上，`LICENSE` 是 MIT。"v1 作为原型仓库"与"同一批代码 v2 闭源"在授权上不成立。要闭源只能换仓库名与包名，从 v2 第一天起就是新的作品。
2. **JS/TS 二进制里的闭源内核是可直接读的。** `bun build --compile` 把源码打进去。字节码编译会拖慢启动，且不是不可逆。真正的门槛不是混淆，是"别把付费能力放在客户端"。
3. **开源用户不会为一个被抽掉内核的壳买单。** 开核心里最挑剔的一群人恰好是目标客户。

**替代方案**（选一个，不要混）：

- **卖团队能力，不卖内核。** 单人版全部开源（含调度器和批量执行）。团队版卖的是共享模板库、审计报告、统一密钥——这些东西天然需要服务端，天然收得回钱，也天然抗破解。
- **卖证据，不卖代码。** 内置的工程范式（模板、规则、验收任务集）持续更新，付费拿订阅更新。这是纯内容，破解无意义。
- **许可证密钥 + 私有仓库在构建期注入，并诚实地写"源码可见"**。技术上挡不住，但商业上够用，前提是别在 README 里承诺"闭源不可破解"。

顺带：**99 元终身**与**19 元/席位/月**定价倒挂。3 人团队年付 684 元，而 3 个终身个人版只要 297 元且永久。团队客户会买 3 个个人版。要么个人版改成 99 元/年（含更新），要么团队版给的是个人版给不了的东西。

还有：**K9999 是《Akira》里的角色名**，商业产品用之前先查一下商标与同名项目。

## 5. 商业数字：算术都对，漏斗不自洽

核算过的部分：

- 1500 × 99 = 148,500 ✓
- 30 × 3 × 228 = 20,520 ✓（19 × 12 = 228）
- 合计 45 万 ✓

不自洽的部分：

1. **"转化率 ≥ 8%" 与 "1500 付费" 同时成立需要 18,750 个进入付费漏斗的用户**，是 SAM（12 万）的 15%。这个数字应该写在 SOM 里，而不是当成转化率。两个数字现在互相矛盾。
2. **"纯利润 ≥ 85%" 不计创始人 12 周的机会成本，也不计终身许可的终身支持成本。** 终身许可是把未来的支持义务一次性卖断，对单人开发者是最危险的一种定价。
3. **只有基准情景。** 建议给三档：悲观 300 付费（≈3 万）、基准 1500、乐观 4000。看悲观档能不能活，那才是有用的判断。
4. **"效率提升 50%"、"轮次减少 45%"、"仅需 3 轮"** 全部没有测量方法。仓库自己的规则（`docs/specs/README.md` 第 4 条）是"未建成的工作不写数字，页面上的数字要有命令能重新生成"。这三句一旦印在 README 上，就必须先有一个能跑出它们的基准。

## 6. 与仓库既有决定的冲突

| 文档 | 冲突的决定 | 说明 |
|---|---|---|
| 0005 `workers/backend-dev.ts` 等 5 个类 | ADR-0004「profile 是唯一的 Agent 类型机制」 | Worker 应当是 `profiles/backend/{profile.json, system.md}`，即数据。5 个类是 5 个需要维护的 TypeScript 模块 |
| 0001「不基于 Pi 内核，从零自研」 | ADR-0017「构建在 pi-durable 之上」 | 这条得显式推翻并写进 decisions.md，不能只在 README 里一句话带过 |
| 0003 §5 验收标准 | specs README 第 2 条「验收必须可运行」 | "可以自动拆分任务"、"不需要多轮思考"只有人能判 |
| 0002 §（五） | specs README 第 4 条「未建成的工作不写数字」 | 全书都是数字，且没有生成命令 |
| 0003 §2.2「审计在团队版」 | SPEC 0011 安全链 | 多 Agent 让审计更必要而不是更晚。5 个 Agent 并行跑命令、没有操作日志，出问题无法复盘 |
| 0003 §4「容器沙箱」 | specs README 第 6 条「可选组件要有定义好的关闭路径」 | 没装 Docker 的用户走哪条路？Windows 上要 Docker Desktop |

另外两处实操缺口：

- 工具面现在只有 `read` / `bash` / `edit`（`packages/core/src/tools/index.ts` 的 `toolNames()`）。**没有 `write`**，也**没有 git**。Demo 用例 1 的第一步就缺工具。`write` 是 `TOOL_FACTORIES` 加一行。
- `k9999 start` 是纯交互式的。eval 与 CI 需要非交互路径，今天有 `--print`，v2 不要丢掉它。

## 7. 文档内部的四对矛盾

1. 立项书开头「总 12 周。MVP 4 周，正式版 8 周，商业化配套 12 周」与里程碑表「第 9–12 周 = 商业化」：前者读起来是 4+8+12 = 24 周。
2. PRD 免费版「仅开启后端与前端两个 Worker」与「无 PTC」：如果 PTC 是引擎级能力，免费版就没有批量工具，那么单 Agent 免费版和 Pi 的区别是什么？
3. README「本仓库 v1 不再迭代内核」与 0001「`k9999-agent-harness` 作为 v1 原型验证仓库」：同一个仓库，两种命运。
4. 0003 用例 2「仅需 3 轮」与用例 1「5 个阶段」：轮次在不同用例里不是同一个单位。

## 8. 建议的替代排期

现在这份计划最大的风险不是技术，是**用 12 周做出一个无法证明它有用的东西**。所以先花 2 周换一个判决。

### 第 1–2 周：一个垂直切片，一个可运行的谓词

范围：空目录 → 架构 Agent 出契约 → 后端 Agent 在 worktree 里写 → 测试 Agent 写测试 → `npm test` 通过。

做的四件事：

1. **`write` 工具**（`TOOL_FACTORIES` 加一行）与 **git 工具**（worktree 与提交）。
2. **`Plan` 类型与校验器**：路径所有权清单 + 接口契约。反对意见必须在架构 Agent 的输出上校验，越界即失败。
3. **`waiting + on + JoinPolicy` 直连 `pi-durable` 的 task graph**，不写新的调度器。
4. **eval 任务集加 5 个 Web 任务**，谓词是"测试通过"。指标固定为：assistant 消息数、工具调用数、token、wall time、到首次通过轮数。

产出是一张表：单 Agent 基线 vs 多 Agent，同一组任务。这张表决定后面 10 周做什么。如果多 Agent 没有赢，赢的可能是"契约"或"验收"，那也是一个真结果，而且更便宜。

### 第 3–4 周：按测量结果选方向

- 多 Agent 赢 → 补前端、Test、DevOps 角色（写成 profile，不写类），补合并与冲突处理。
- 只有"契约 + 并行"赢 → 砍掉部分角色，把并行做深。
- 都没赢 → 转向"可判决的验收 + 工程模板"，这是仓库今天真正独有的东西。

### 明确砍掉的东西

- Bun 重写：推迟到分发阶段，先用 `bun build --compile` 打包现有代码试装。
- 容器沙箱：v1 只生成 Dockerfile，**不执行** `docker`。执行远程部署需要网络与凭据，是最容易造成真实损失的一步。
- 5 个 Agent 一次上齐：先上 2 个，把并发正确性做对，再加第 3 个。
- 权限与审计下沉到团队版：审计是调试手段，不是合规装饰。多 Agent 之下它是刚需。

## 9. 需要你决定的四件事

1. **技术路线**：继续在 `pi-durable` 上加多 Agent（推荐），还是按立项书从零起一个 Bun 仓库？如果是后者，`docs/decisions.md` 需要一条显式推翻 ADR-0017 的记录。
2. **卖什么**：卖团队协作能力（推荐，收得回钱），还是卖内核二进制（技术上挡不住）？
3. **先证明什么**：接受"2 周切片 + 一张测量表"作为开工前提，还是先按 12 周把功能铺开？
4. **是否保留 v1 仓库的规则**：确定性验收、数字要有生成命令、未建成的不量化。这三条会让 12 周计划变慢，也会让 README 上的每一句话都站得住。我建议保留，因为它们正是竞品最缺的东西。
